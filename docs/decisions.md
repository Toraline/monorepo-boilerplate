# Decisions

Technical decisions of this repository, newest first. An agent that decides an open choice writes it here, and lists it in the pull request.

Format of one entry:

```
## <YYYY-MM-DD> - <short title> (<TICKET-ID>)
- Decision: <what was chosen>
- Why: <one or two sentences>
- Alternatives: <what was not chosen, one line each>
- Decided by: <the person, or "agent, to be confirmed in review">
```

Two words in the entries:

- **The owner**: the person who owns this repository and decides what an agent may not decide.
- **The earlier private project**: a private repository of the owner, older than this one. Some of the first choices of this repository follow it or differ from it on purpose. Its name is not written here.

An entry says what was true on its date, and it is not rewritten later. Entries before 2026-11-16 say that this repository is private and that no release exists. Since then, release `0.1.0` was published (2026-11-16), and the repository was prepared to become public (TOR-1227).

## 2026-11-16 - Two repositories: the work in monorepo-boilerplate-dev, one commit per release in monorepo-boilerplate (TOR-1234)
- Decision: the development repository is `Toraline/monorepo-boilerplate-dev` (private). The public repository is `Toraline/monorepo-boilerplate`. It gets one commit per release, the release tags, and no private history. The two npm commands download the boilerplate from the public repository, as before.
- Decision: the **public copy** of a commit is made by `boilerplate/public/make-public-copy.sh <new folder> [<commit>]` (`make public-copy OUT=<folder> [REF=<commit>]`). The steps:
  1. It writes every file that git tracks at the commit, with `git archive`. So the same commit always gives the same files.
  2. It leaves out each path of `boilerplate/public/private-files.txt`. Today: `.github/workflows/release.yml` and `local-docs`.
  3. It copies each file of `boilerplate/public/overlay/` to the same path from the root folder. Today: `.github/workflows/check.yml` and `.github/workflows/publish.yml`.
  4. It runs `scripts/check-secrets.sh` over every file of the copy, for secrets and for private names. With a hit it ends with code 1 and names the file. It never prints a name.
- Decision: the 5 files of `boilerplate/public/` are part of the public copy. A monorepo that is created by a command comes from the public copy, so the tests of the commands create it from the public copy too: the test helper `templateRepositoryOfThisCheckout` runs `make-public-copy.sh --apply-rules`. The create manifest is written for the public copy: it deletes `.github/workflows/publish.yml`, and it takes the trigger `push` out of `check.yml`. A new monorepo gets no file of the release flow: the folder `boilerplate/` and `docs/releasing.md` were already in the list of the manifest.
- Decision: the workflow "Release" of the development repository (`.github/workflows/release.yml`) is started by hand with the input `version`. Its guards: the branch is `main`; the version is the version of `boilerplate/VERSION` and of the 2 `package.json` files; the version is higher than the newest tag of the public repository; the version is not on npm. Then `make check`, the public copy, and `boilerplate/public/push-release.sh`: ONE commit on the branch `release/v<version>` of the public repository, with `main` of that repository as its parent, the message `release: v<version>` and the titles of the updates file; then the pull request `Release v<version>`, with a body made by `boilerplate/public/release-text.mjs` from the updates file. The author of the commit is `github-actions[bot]`. The workflow creates no tag and publishes nothing.
- Decision: the message of the release commit ends with the line `Development commit: <commit id>`. No tag is created in the development repository, so this line is the way to find the commit of a release there. A commit id holds nothing private.
- Decision: the public repository has 2 workflows. "Check" is the check of the development repository, and it also runs on each push to `main`. "Publish" runs on each push to `main` and never on a pull request. When `boilerplate/VERSION` holds a version whose tag does not exist, it lints, tests and builds the two commands, creates the tag `v<version>` on the commit, and publishes the 2 packages with `--provenance`. When the tag exists on another commit, it does nothing. When the tag exists on the same commit and a package is not on npm, it goes on with the release: this is the case "the tag exists, npm failed", after **Re-run all jobs**. It has 4 jobs, each with its own permissions: `decide` and `check the commands` read; `create the tag` has `contents: write`; `publish to npm` has `id-token: write` and the secret.
- Decision: the secrets. In the development repository: `PUBLIC_REPO_TOKEN`, a fine-grained personal access token for the public repository only, with 3 repository permissions: Contents, Pull requests and Workflows, each "Read and write". The ticket named 2 permissions. The third is needed: GitHub refuses a push that adds or changes a file of `.github/workflows/` without it, and every release holds those files. Optional: `PRIVATE_NAMES`, the lines of the names file, so that the workflow can check the copy for private names; without it the workflow checks only for secrets and prints a warning. In the public repository: `NPM_PUBLISH_TOKEN`, an npm token for the 2 packages.
- Decision: the rulesets of the public repository. `protect-main`, made by `scripts/protect-main.sh --repo Toraline/monorepo-boilerplate`. `protect-release-tags`, for the tags `v*`: it forbids changing and deleting a tag, and it does not forbid creating one. So the workflow "Publish" can create a tag with the token of its run, and nobody is on a bypass list.
- Decision: the **seed** of the public repository is a local git repository with 3 commits: the files of the tags `v0.1.0`, `v0.1.1` and `v0.1.2` of the development repository, with the messages `release: v0.1.0`, `release: v0.1.1` and `release: v0.1.2`, the same tags (lightweight, as in the development repository), and the dates of the original commits. The ticket names 2 commits; the third is there because `0.1.2` was published during this work (the entry above). The list of private files and the overlay are not applied to these 3 releases: the published commands expect the files that their own manifest names. The owner pushes the seed.
- Decision: the files of `v0.1.1` and of `v0.1.2` in the seed are exactly the files of the tags. The files of `v0.1.0` differ in 2 files, not in 1 as the ticket expected: `docs/decisions.md` (each private name became "the earlier private project" or "the owner") and `agent/skills/define-app/SKILL.md` (one example of an app name became `recipe-box`, the example that `0.1.1` has). The second file also held a private name.
- Checked on 2026-11-16, on one machine: (1) no file of any commit of the seed holds a private name, a secret or a personal path; (2) the published commands `create-toraline-monorepo@0.1.2`, `@0.1.1` and `@0.1.0` created a monorepo from the seed, `make setup` and `make check` passed in the monorepos of `0.1.2` and `0.1.1`, and `update-toraline-monorepo --check` gave the expected answer in both; (3) the flow was tried without GitHub: the public copy of this branch was sent into a copy of the seed that held `0.1.0` and `0.1.1`, with `make-public-copy.sh` and `push-release.sh`, and the commands built from this branch created a monorepo from that copy and updated one from `0.1.1`.
- Why: the history of the development repository holds private names, and a public repository shows its whole history. One commit per release shows only what a release holds. A pull request per release gives the owner one place to read everything that becomes public, before it is public.
- Alternatives: rewriting the history of the development repository and making it public (every old commit and every pull request would have to be cleaned, and one missed name is public for ever). A fork as the public repository (a fork of a private repository cannot be public). The tag and the npm publish in the development repository (the commands download from the public repository, so the tag must be there; npm gives provenance only to a public repository). A bypass list for the tag rule (the token of a run cannot be put on it with the buttons; a rule with no creation limit needs no bypass). A copy with a list of the files that ARE public (a new file would be forgotten and missing in a release; with a list of private files, a forgotten private file is found by the name check and by the review of the pull request).
- Known limits: no workflow has run on GitHub yet; the first run is the next release. A pull request from another person to the public repository cannot be merged there: the owner applies it in the development repository (`CONTRIBUTING.md`). The author of the 3 commits of the seed is the git identity of the owner's machine, as the ticket asks: that name becomes public with the push. A person with write access to the public repository can still create a tag `v*` by hand.
- Decided by: the owner for the model (the ticket); agent for the details, to be confirmed in review

## 2026-11-16 - One script protects the branch main on GitHub; the guide and the skill /start ask once (TOR-1234)
- Decision: `scripts/protect-main.sh` creates one ruleset with the name `protect-main` for the branch `main`, with the `gh` command. Its 4 rules: a pull request is required, with 0 approvals; the check must pass; no force push; no deletion. The name of the check is read from `.github/workflows/check.yml`: the `name:` of its first job, or the id of that job. With no such file, the ruleset requires no check, and the script says so.
- Decision: the script prints what it will create, and creates it only with `--yes` or after the person types `yes`. Where no question can be asked (no terminal) and `--yes` is missing, it changes nothing and ends with code 1. It does nothing when a ruleset with the name `protect-main` exists. When GitHub answers 403, it says that the plan of the owner does not allow rulesets on a private repository, or that the person is not an admin.
- Decision: `--status` changes nothing and prints one word: `protected`, `not-protected`, `no-github-remote` or `unknown`. The skill `/start` reads it in a new Part B. With `not-protected` it asks one question, "Protect the branch main now?", and runs the script on a yes. It writes the answer into `local-docs/notes/protect-main.md`, so the question is asked once.
- Decision: `make protect-main` is in the `Makefile` of the root, not in `agent/core.mk`. The step is named right after `gh repo create` in `docs/start-a-new-monorepo.md` (step 10, point 5) and in the next steps that `create-toraline-monorepo` prints. `scripts/sync-skills.sh` copies the script as a core script.
- Decision: a monorepo gets it in 3 updates of `0.1.3`. `0.1.3-core` (core files, applied by the command): the skill `/start`. `0.1.3-protect-main` (core files, applied by the command): the script and `scripts/sync-skills.sh`. `0.1.3-protect-main-target` (new feature, applied by an agent): the target in `Makefile` and the lines in `AGENTS.md` and in the guide. The command cannot merge a line into a `Makefile` that a project changed.
- Why: a new repository on GitHub lets everyone with write access push to `main`, force push and delete the branch. One question at the right moment costs one answer, and the rule is the same in every monorepo.
- Alternatives: the classic branch protection of GitHub (one rule per branch with more settings; rulesets are the current form, and one can be read by its name). Creating the ruleset inside `create-toraline-monorepo` (the command creates nothing on GitHub, by design). Asking at each `/start` (a person who said no would be asked again each time).
- Known limit: the script was tested with a program that stands in for `gh`. It was not run against GitHub.
- Decided by: agent, to be confirmed in review

- Decision: `create-toraline-monorepo` and `update-toraline-monorepo` stop when the value of `--source`, of `TORALINE_BOILERPLATE_SOURCE` or of `--ref` starts with `-`. - Decision: both workflows name each action by the full id of a commit, with the version in a comment: `actions/checkout` v4.4.0, `actions/setup-node` v4.4.0, `actions/setup-python` v5.6.0, `actions/upload-artifact` v4.6.2. ## 2026-11-15 - Each worktree has its own database (TOR-1095)
- Decision: the main checkout and each worktree run their own PostgreSQL container with their own volume. `docker-compose.yml` sets no container name and no project name, so Docker Compose names both after the folder of the checkout. The main checkout uses port 5432. When a worktree is created, `scripts/worktree-setup.local.sh` writes the first free port from 5433 up into the worktree's `.env` (`POSTGRES_PORT`). A port counts as taken when a program listens on it or when the `.env` of another worktree of this repository names it. The port is bound to `127.0.0.1` only.
- Why: two branches can have different database tables. With one shared database, the tables of one branch break the other branch, and two test runs at the same time use the same test database. A separate database per worktree removes both problems, and `make db-reset` in a worktree deletes only that worktree's data.
- Alternatives: one shared database for every checkout, as in the earlier private project (`COMPOSE_PROJECT_NAME` set to the name of the main checkout): one container and one port, but the problems above. One shared server with one database name per worktree: one container, but the Makefile would have to create and drop databases itself.
- Known limit: `make worktree-remove` does not stop the worktree's container and does not delete its volume. Run `make db-destroy CONFIRM=yes` in the worktree before removing it. Two clones in folders with the same name share one Compose project name; give one of them a `COMPOSE_PROJECT_NAME` in its `.env`.
- Decided by: agent, to be confirmed in review.
